00两个前提发现

03Dependency：每请求一次的环境装配器

不需要理解 FastAPI 依赖注入的底层实现，只需要知道它在当前骨架里扮演的角色和生命周期。

问题真实答案
SessionDep 从哪来 backend/app/api/deps.py:21-26：get_db() 是生成器，with Session(engine) 打开会话后 yield session。SessionDep = Annotated[Session, Depends(get_db)] 只是类型别名——endpoint 签名写 session: SessionDep 就等于声明「我要一个会话」。
CurrentUser 从哪来 backend/app/api/deps.py:30-49：OAuth2PasswordBearer（:16-18）从 Authorization 头抽 token → jwt.decode（SECRET_KEY + HS256）验签 → 取 sub（= user.id）→ session.get(User) 查库 → 校验 is_active → 返回 User。注意依赖可以叠依赖：get_current_user 自己签名里就有 SessionDep 和 TokenDep。
谁创建 Session get_db 里的 with Session(engine)，每请求一次；engine 是进程级单例（backend/app/core/db.py:7），负责真正的连接池。
谁解析 JWT get_current_user（没有独立的 auth 模块）。token 的签发在另一端：backend/app/api/routes/login.py:24-43 调 backend/app/core/security.py:22-26，默认有效期 8 天；前端存 localStorage（frontend/src/hooks/useAuth.ts:46），每次请求由 frontend/src/main.tsx:19 取出。
endpoint 为什么不用自己建 FastAPI 调用函数前看签名：遇到 Depends 就先执行依赖函数，把结果当参数传入。写 session: SessionDep, current_user: CurrentUser，进函数体时两个对象已就位。
请求结束后 Session 怎么处理 endpoint 返回、响应序列化完后，FastAPI 恢复 get_db 生成器，with 块退出 → session.close() → 连接还回池。没有全局事务包装、没有自动 commit、也没有显式 rollback——commit 完全是业务代码的责任，不 commit 的改动随 close 丢弃。
一句话

Dependency 在这个骨架里就是「每请求一次的环境装配器」。业务代码拿到 session 不是因为有魔法，只是签名声明了 SessionDep，FastAPI 调你之前先替你跑了 get_db()。

04Schema / Model 的真实关系

本版本没有独立 schemas.py——Item 家族全部在 backend/app/models.py，靠 SQLModel 继承分出三个角色。下树中的行号均指该文件。

  • SQLModel
    • ItemBase:115 · title(1..255) / description(≤255) · 字段共享基类
      • ItemCreate:121 · 空壳 — ① 创建请求体
      • Item (table=True):132 · +id / created_at / owner_id(FK→user.id, CASCADE) / owner — ② 数据库表
      • ItemPublic:145 · +id / owner_id / created_at — ③ 返回形状
    • ItemUpdate:126 · 独立基类，全字段可选 — PUT 请求体
    • ItemsPublic:151 · {"data": list[ItemPublic], "count"} — 列表响应

为什么表模型和 API 模型不是同一个类

三个角色约束不同：入参不能让前端指定 owner_id（归属由服务器定）；表模型带 owner 关系等内部字段；响应要控制暴露面。本项目的 GenerationJob.requirement 在 GenerationJobPublic（backend/app/models.py:357）里对学生置 None——就是靠分开才能做得到的脱敏。合成一个类，任何改动都会同时冲击三个方向。

数据形态的两次变化

  • JSON → Python：ItemCreate 在 FastAPI 调 endpoint 之前由请求体构造（失败 422）；ItemCreate → Item 在 backend/app/api/routes/items.py:68 的 model_validate。
  • Python → JSON：endpoint return item 之后，FastAPI 按 response_model=ItemPublic 校验+序列化。列表路由 backend/app/api/routes/items.py:44 还有显式写法 ItemPublic.model_validate(item)——两种风格并存，效果一致。

05业务逻辑到底在哪（诚实版）

不预设存在 Service Layer——真实答案是：就在 Router 文件里。

create Item 的真正业务逻辑是 backend/app/api/routes/items.py:68-71 这四行（validate / add / commit / refresh）。没有 Service，也没有走 crud。

容易被骗的点

backend/app/crud.py:63-68 存在一个几乎逐行相同的 create_item，但只被测试工具 backend/tests/utils/item.py:16 调用——生产代码不用它。CRUD 层是「半残」的：User 相关（注册、认证、改密）确实走 backend/app/crud.py；Item 的五个 endpoint 全部 Router 内联。

HTTP 层与业务逻辑的真实边界

  • HTTP 层该做的（确实做了）：URL/方法声明、依赖装配、入参/出参 schema、状态码与异常（404/403）。
  • 业务逻辑（但混在 Router 里）：owner_id 赋值规则、model_validate 转换、持久化三步、读列表时「superuser 看全部 / 普通用户看自己的」分支（backend/app/api/routes/items.py:21-42）。

对本模板这样是合理的：CRUD 密度极低时，多一层转发只是仪式。边界在「业务逻辑超过一屏、或需要被多个 endpoint 复用」时到达——本项目的 backend/app/api/routes/ask.py 已经越过这条线（一个 endpoint 里 130 行编排逻辑），说明项目实际已经长出了对 Service 层的需求（backend/app/services/ 目录就是证据，见第 10 节）。

  1. 后端加好 endpoint（带 tag、request / response 模型），启动后端。
  2. 把 /api/v1/openapi.json 的内容更新到 frontend/openapi.json。仓库里没发现自动做这一步的脚本（backend/scripts/ 只有迁移/测试类脚本），更新方式无法从当前代码确认，应是手动或文档约定的流程。
  3. cd frontend && npm run generate-client（frontend/package.json:11 → openapi-ts）重新生成 frontend/src/client/。
  4. 前端代码 import 新生成的 Service 方法使用。

backend/app/services/ 目录已存在（dify.py、llm.py、openmaic.py、snapshot.py、storage.py），backend/app/services/__init__.py 为空——没有注册机制，直接 import 用。消费方式见 backend/app/api/routes/ask.py:131-134：

except llm.LLMError as e:

Service 是普通 Python 模块/函数，不碰 HTTP 对象；它抛领域异常，Router 负责翻译成 HTTPException。这就是当前骨架事实上的接入模式（函数式而非类式，但 ExampleService 这种类写法同样成立）。

execute() 最适合的调用位置：Router endpoint 内部，依赖装配之后、response_model 序列化之前——endpoint 只做「取参 → 鉴权（如需）→ 调 service → 把结果映射成响应 schema」。

完全不需要改的现有机制

backend/app/api/deps.py 全部依赖、engine/Session 生命周期、JWT 认证链、CORS、config 单例、alembic（不动表时）、前端 token 注入与全局错误处理、client 生成管线。这就是「能自然接入」的直接证据：四个入参在当前骨架里全都有现成的、彼此正交的来源。

Service 复杂起来后，可能要调整骨架的地方（按优先级）

  1. 事务边界——最实质的缺口。commit 散落在每个 endpoint/业务处，get_db 只 close 不 rollback 也不包事务。Service 多步写操作必须先约定「谁 commit」（推荐：Service 不 commit、endpoint 统一 commit；或包一层 UoW）。骨架不阻止任何一种，但也没有任何一种的惯例。
  2. 领域异常 → HTTP 的映射。目前每个 Router 手写 try/except 翻译（backend/app/api/routes/ask.py 翻成 502）。Service 多了以后值得加统一 exception_handler，但这是渐进的。
  3. models.py 单文件。已近 400 行、7 个域混在一起，业务变多后拆分是组织问题（不影响接入机制）。
  4. 前端 403 误伤。frontend/src/main.tsx:24 把所有 403 当登录失效踢出，Service 引入更细的权限错误后会放大这个问题。
  5. 外部调用治理。backend/app/services/ 里对 Dify / LLM / OpenMAIC 的超时、重试约定，本次未逐一核对代码，无法确认是否已有统一配置——接入前值得看一眼。
结论

别人写好的 ExampleService 可以自然接入当前模板——参数来源、调用位置、文件落点全部现成。模板真正缺的不是「接入口」，而是团队级的两条约定：事务边界归谁管、领域异常怎么翻译。这两条不定，Service 一复杂就会出现「半个 router 半个 service 都在 commit」的混合态——而 Item 自己现在就是这个状态的缩影（items.py 内联版与 crud.py 孪生版并存）。
