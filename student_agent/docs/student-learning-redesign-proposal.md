# 学生端播放后学习流程与后端改造建议（讨论稿 v0.8）

日期：2026-10-26。用户确定的首要目标：学生能够解释概念，并在新问题中独立应用。本文是待讨论的设计建议，不是已实现功能或已验证效果的承诺。

当前试用方向：Agent 根据学习证据决定继续当前主题、换主题或进入独立尝试；程序按预设流程边界校验并执行推进。Agent 决定教学动作，程序拥有实际状态与执行权，教学模型提供具体内容。当前设计以 [dialogue-tutoring-design.md](dialogue-tutoring-design.md) 为准，尚未修改业务代码。本文后续旧题组、分类与阶段细则仅作历史参考。

本轮修订依据：用户确认当前稳定输入是教师原版 PPT 和生成的 HTML 课件；整段播放保留，讨论重点是播放后的学习。前版把代码支持的可选产物作为设计基线不够准确，本版取消这种依赖。产品比较见 [material-based-products-research.md](material-based-products-research.md)。

已确认继续保留：原 PPT 和生成 HTML 输入、整段播放、以学生实际表达为教学依据。Agent 在允许范围内选择教学目标和下一动作，程序校验后更新状态并推进；不要求先完成固定题组才能获得帮助。

历史题组设计见 [diagnostic-tutoring-detailed-design.md](diagnostic-tutoring-detailed-design.md)。此前选择/判断配简答、建议4题以及固定表现分类已受到用户质疑，当前不作为硬约束。

外部参考见 [product-native-workflow-options.md](product-native-workflow-options.md)。本轮主要借鉴材料型开放引导与基于具体学习记录的辅导，属于本项目适配，不要求复刻某款产品全部功能。

## 1. 建议方向

程序主线草案为“整段播放 → 开场交流 → 当前教学任务循环 → 独立尝试 → 总结反馈 → 结束”。Agent 在预定义动作与合法分支中作教学决策，程序负责前置校验、状态更新和执行；模型自由文本不能直接推进。具体动作契约、推进条件和负担限制仍待细化。

整段播放是固定约束，不列入分段改造路线。后端可在播放期间准备带出处的主题和任务候选；学生看到的学习活动从播放后展开。沿用 FastAPI、LangGraph 和 PostgreSQL，先把流程讨论清楚，再决定实现范围。

## 2. 当前流程为何难判断效果

当前流程并非毫无价值：逐点复述、反馈和纠错已经提供了主动学习机会。不过它缺少足够的证据区分以下情况：

- 学生原来就会，还是在这节课学会。
- 学生借助提示说对了，还是能够独立说明。
- 学生记住当前问题的回答，还是能解决不同情境的问题。
- 学生刚学完能够回答，还是过一段时间仍然会。

固定 8 轮/4 轮主要控制流程长度，不能直接定义掌握。现有讨论结果与概念结果分开保存是值得保留的设计，但还应显式保存题目、帮助程度和独立表现。目前讨论原题主要隐含于消息历史，新版应建立稳定 taskId 和题目对象。

## 3. 仅依赖 PPT 与 HTML 怎样接入

本版只把下列两项作为稳定输入，不能要求教师额外生成目标、知识点、习题和量规。

| 稳定输入 | 新学生端用途 | 当前接入条件与限制 |
|---|---|---|
| 教师原版 PPT | 核对概念、公式、图示、案例与原文依据，定位页码 | 当前学生主链尚未直接消费完整 PPT；需从平台提供解析内容，图表/公式不能只按纯文字处理 |
| 生成的 HTML 课件及可获得的讲解数据 | 确认实际呈现的内容、顺序和例子，定位页面或场景 | 当前主链已提取场景文字与 speech 旁白；不能假定所有外部 HTML 都有相同结构或旁白 |

代码补充核查：`course-artifact-runner.ts` 和 `classrooms/attach/route.ts` 的部分路径会调用 `ensureLessonReviewFiles`；其新建目标/知识点文件状态是 draft，并不等于已发布给学生。习题、评价标准和图谱等也不能作为必有输入。以后若有明确发布的补充材料，可以增强方案，但不阻塞基础流程。

优先沿平台 learning-context 扩展统一契约。教师端已有 student-agent 服务接口，可作为平台适配层的取数方式；学生浏览器仍通过平台身份与课时权限进入，不自行调用服务密钥接口。

### 3.1 范围与内容冲突处理

- 只纳入当前课时明确发布的目标和资源，以及教师明确标记可共享的材料。
- 从课件中归纳“可检查的理解点”，标记为系统推导，不冒充教师明确制定的教学目标。
- 播放内容确定本次学习范围，原 PPT 用于核对与解释；原 PPT 有而课堂未呈现的内容不能直接作为必答要求。
- 任务可以使用新情境，但所需知识必须来自本课；新情境的必要信息应在题干给全，不能悄悄要求额外学科知识。
- PPT 与 HTML 矛盾或引用无法定位时，标记内容冲突，不据此给学生确定的错误结论。
- 参考解答、评分要点、提示和变式由学生端后台准备，均属于系统生成候选；检查与原材料是否一致。首批试点抽样核查，不新增教师必须逐题维护的日常前置流程。
- 图像、公式或动态内容无法可靠提取时，收缩可检查范围，不能默认没提取到就代表没讲，也不能凭空补齐。

### 3.2 课时教学包（建议新增）

此处“教学包”是学生端内部准备结果，不是新增教师交付物。先准备可检查理解点、来源、任务、判定依据和提示即可；按版本缓存，避免每个学生重新生成整套内容。

```text
LessonLearningPackage
  lessonId / packageId / compilerVersion
  sourceManifest[]      资源ID、发布ID、内容hash、归属
  objectives[]          系统推导的可检查理解点、可观察行为、来源与推导标记
  concepts[]            概念ID、先修项、引用依据、场景映射
  tasks[]               题干、类型、目标ID、变式族ID、使用角色
  rubrics[]             关键标准、可接受答案、错误类型、证据出处
  teachingSupports[]    提示层级、相关例子、对应材料
  coverageGaps[]        材料不足、冲突、目标未覆盖
  validationStatus      草稿/规则校验通过/教师确认
```

练习题与独立验证题区分角色；答案、量规与保留验证题留在服务端，不随页面课程包整体下发。题干本身要足以作答，不能依靠学生猜测模型隐含条件。

缓存键应包含各资源发布ID与内容hash，不能只依赖课程总包版本；现有个别发布路径不一定每次更新课程总包版本。会话固定使用一个教学包版本，撤回资源时重新校验使用资格，不静默改写历史证据。

## 4. 推荐学习流程

### 4.1 整段播放后的初步理解检查（已选方向，细则待讨论）

不增加强制课前诊断。播放结束后先用一小组代表性任务发现困难，例如解释核心关系、辨别误解、简单应用；当前建议为 3 道选择/判断＋1 道简答，数量仍应结合课时与负担调整。自述不清晰也可能来自表达困难，先澄清再判断概念问题。

遵循用户选择的“比较简单”：以本课核心内容和短回答为主，不在入口放长篇复述或复杂综合案例。判断/选择题可配一句简短理由，以便区分猜对和理解；这是候选题型，最终配比待定。难度、数量和回答负担应随真实课时校准。

允许回答“不知道”、提问、暂停或暂时跳过。少量任务只能覆盖采样到的理解点，未覆盖内容标记“未验证”，不能由 3 个题推出整节课全部掌握。学生说“我懂了”或“我不确定”用于调整辅导，不单独作为能力结论。

初步检查得到的是“看完本课后、接受这轮个别辅导前”的状态，不是课前基础测验。它可以用于安排后续辅导；仅凭这一份结果无法证明视频带来了多少学习提升。

建议按如下方式设计和使用题目：

| 任务角色 | 想观察的表现 | 出题要求 |
|---|---|---|
| 核心理解 | 是否理解本课的核心含义或关键关系 | 避免只要求复述定义；可以简短回答 |
| 辨析判断 | 是否能分清容易混淆的情形、适用条件或错误解释 | 尽量要求给一个理由，减少猜对的影响 |
| 简单应用 | 是否能用刚学的概念处理一个小问题 | 给全必要信息，难度不超出本课讲授 |

这三类是候选角色，不强制每节课各出一题；具体数量取决于内容和负担。题目对应不同核心理解点，避免围绕同一细节反复发问。首版可先用一组预先校验的代表题；诊断阶段自适应选题属于后续可选项。

交互细则建议：逐题呈现，先收集这一小组的原始回答，再进入完整讲解；不展示答案或长篇纠错，以减少前题辅导影响后题诊断。允许中性澄清题意，但若提供概念提示、示例或答案，就显式记录帮助，并将相应表现标为受助证据，不作为原始独立表现。学生主动提问时不强行阻断，愿意继续检查时再恢复。

初步检查输出应按“理解点”记录，而非只生成总分或给学生贴强弱标签：

同时形成便于规划的整体摘要，例如“本次抽查中基础概念表现较好，B 存在误解，C 的简单应用需要帮助”。整体摘要必须关联下述具体证据，并写明未覆盖范围，不能只按正确题数给出整节课确定掌握率。

```text
本课初步理解概况
  理解点 A：已展示独立解释；依据是题目1的回答
  理解点 B：存在具体误解；依据是题目2的理由
  理解点 C：理解概念但应用证据不足；依据是题目3的步骤
  理解点 D：未覆盖，尚不判断
```

每项保存任务ID、原始回答、对应材料、满足/缺失的判定要点、帮助记录及不确定原因。未回答、表达含糊、明确错误和材料/题目本身有问题需要分开处理。

辅导安排由此生成并持续更新：先处理影响当前任务的核心误解，再帮助把概念用于问题；已展示理解的点减少重复，未覆盖的重要点可以在后续任务中补查。无需预先固定“所有人必须完成相同的加强轮数”。

### 4.2 根据初步表现安排辅导

后续大模型接收本课内容依据、题目与学生原始回答、逐题判定和帮助记录、整体摘要及未覆盖项，据此提出短的辅导安排：优先处理什么、采用哪种解释/练习、接下来怎样检查。不能只传一个总分，让模型凭分数猜学生哪里不会。

模型可选择讲解、澄清、例子、提示、简单练习等教学活动；系统负责核对所选内容属于本课、任务来源有效、帮助与独立表现被正确记录，以及是否已触及约定的轮次/时长边界。具体约束待实现设计确定。

短检查之后，只对证据不足或出现误解的部分开展解释、对比、反例或小任务。多个紧密相关的知识点可以合并处理；已独立完成的部分减少重复，不按所有知识点各走固定轮数。

建议呈现一个短的下一步说明，例如“你已经能解释 A；接下来先分清 B 的两个情形，再练一次 C 的应用”，让学生知道为什么进入当前活动。该安排是可更新的：后续回答出现新证据时重新调整，不把开场结果永久固定为学生能力。

此处学生可以随时提问、请求说明或暂停；自由提问不必被“全部补完后才允许”的硬门槛阻断。回到练习时恢复原任务，保留未验证目标。

### 4.3 按错误类型提供帮助

| 表现 | 建议下一步 |
|---|---|
| 不理解词义或关键关系 | 引用本课材料，简短解释并让学生辨析 |
| 混淆两个概念 | 给对比例或反例，再检查区别 |
| 概念能解释，方法不会用 | 提供一个例题或第一步，让学生完成剩余步骤 |
| 在帮助下完成 | 改用新变式，并逐步减少提示 |
| 独立答对且理由成立 | 进入新的应用情境或结束当前目标 |
| 多次无进展 | 暂停追问，提供不同方式的教学或记录待巩固，允许结束 |

轮次上限继续存在，作用是防止疲劳和无限追问；到上限不等于掌握。具体轮数、课时练习时长和每目标题量通过试点调整。

### 4.4 独立应用验证

学生得到帮助后，需要在一个未展示答案的新任务中独立完成，并解释为何使用这个概念。换数字通常只能验证同类操作；要验证应用，需要改变情境、信息组织或方法选择要求，同时保持在本课实际讲授的知识范围内。

验证时允许求助，但一旦给出内容性提示，这次就转为练习证据，之后另选新任务验证。答错可以进入教学，不能反复泄露同一验证题答案再算独立通过。

首版示例通过规则：核心标准全部满足、无关键概念错误，且同时具有独立解释与新情境应用证据，才能标记“本次独立应用已验证”。这是待校准的产品规则，不是通用科学阈值；不同学科目标允许不同标准。

### 4.5 课后复查

结束时给出已验证能力、仍依赖帮助的能力、待补任务及依据。将延迟复查设为产品内待办，在之后登录或下一次课堂时出现；是否通知和何时通知属于后续产品设计，本方案不创建任何自动化。

数日后使用不同题目复查关键目标，具体间隔是试点参数。未参加或未到复查时间标记“未验证保持”，不标记遗忘，也不凭一次即时正确标记长期掌握。

## 5. 用证据表示学习状态

把现有单一 mastered 拆成多个可解释维度：

| 维度 | 证据 |
|---|---|
| 概念理解 | 独立解释核心关系，辨认典型误区 |
| 支持下应用 | 看提示或例题后完成任务 |
| 独立应用 | 在新问题中无内容提示完成关键要求 |
| 延迟保持 | 间隔一段时间后仍能独立完成 |

不需要把这些伪装成精确百分比。状态可用“未知/需要支持/已获得独立证据/待复查/证据冲突”。保留历史证据，也允许较新的失败触发复查，不再只累积最高分。

每次尝试至少记录 taskId、目标、题目版本、原始回答、逐标准判定及回答原文依据、提示等级、是否看过答案、是否重复题/同题族、时间、使用模型及提示词版本。模型无法可靠判断时返回 uncertain，追加澄清或交由抽样复核；不要把模型自报置信度当成经过校准的掌握概率。

若题目适合规则判定，例如计算结果或有限选项，优先用明确规则或执行结果验证，同时另行评价解释。对于开放答案，要求按量规判定，接受不同措辞与合理不同解法。判定组件和教学回复组件可复用现有模型，但职责与输入分离；分开调用本身不保证判断独立或正确。

## 6. 一个学生实际会经历什么

以下以“相关与因果”为说明性例子，不代表仓库现有课程。

1. 目标：能解释相关不一定代表因果，并说明需要什么证据。
2. 保留完整观看教师课堂。
3. 播放后短检查：两件事同时增加，能否认定一件导致另一件？说明理由。
4. 若学生直接下因果结论，导师给提示：“有没有第三个因素可能同时影响它们？”
5. 学生经提示修正，记录“支持下完成”，继续一个新的情境。
6. 独立验证：“参加某学习活动的学生成绩更高，能否据此断言活动有效？还应检查什么？”
7. 根据系统从课件准备并核查的判定要点评价是否识别其他解释、是否给出合理验证思路，保留原始回答；教师另有发布标准时可补充采用。
8. 下一次学习时用不同领域例子复查，观察是否还能使用同一判断原则。

## 7. 后端建议分工

```text
平台与教师发布资源
        ↓
课时适配与教学包编译 → 包质量检查/人工确认 → 版本缓存
        ↓
学习会话服务 → 当前任务 → 学生回答
                              ↓
                       按量规评估
                              ↓
                       保存尝试证据
                              ↓
                       策略选择下一步
                              ↓
                       教学回复/新任务
```

建议逐步从 main.py 中分出：

- lesson_adapter / lesson_package：统一来源、范围、版本、目标和任务。
- assessment：基于固定题目与量规评估；输出标准结果及依据。
- learning_policy：用可测试的规则选择讲解、提示、变式、验证、结束或复查。
- learner_state：由尝试证据维护多维能力状态。
- tutor：在确定的任务和帮助级别内生成回复。
- review / feedback：课后待办、个人反馈及教师端聚合。

LangGraph 继续承担编排。数据库新增或扩展教学包、任务、尝试证据、目标状态、复查待办对象；聊天消息保留，但不承担所有业务事实。对学生请求使用幂等 attemptId，以事务保存本轮证据和状态变化，避免重试重复计算。

服务端数据库成为跨浏览器学习状态依据，浏览器保存恢复指针和显示缓存。后台教学包生成可先做简单持久任务状态，扩展多实例时再引入共享任务队列。教师端学情同步补齐可靠发送与重试，分别呈现课堂完成、概念理解、独立应用和待复查，避免混成一个百分比。

## 8. 怎样知道是否真的有效

### 8.1 先检查判定可信度

选少量真实课时建立教师标注样本，覆盖独立答对、提示后答对、措辞不规范但理解正确、说出关键词但理由错误、无关回答和评价歧义。

盲评对照模型判断与教师标准，重点检查“误判已掌握”和“把合理答案判错”，记录分歧并修改量规。不能只使用生成题目的模型为自身教学效果打分。

### 8.2 再检查教学效果

先小规模验证可用性，之后在条件允许时把学生随机分配到现有流程和新版流程，使用同一课程内容、对等的测验条件、平衡的题目版本。预先确定主要结果与分析方式；如果按班级分组，应考虑班级差异与聚类，避免把同班学生当作完全独立样本。

| 指标 | 用途 |
|---|---|
| 课前基础 | 解释学生起点差异 |
| 未练过的即时应用题表现 | 看是否能迁移到新问题 |
| 延迟应用题表现 | 推荐的主要效果指标之一，看保持和迁移 |
| 无帮助完成比例与帮助次数 | 区分独立能力和依赖提示 |
| 学习用时、退出率、挫败反馈 | 检查学习收益与额外负担 |
| 判定与教师盲评的分歧 | 检查“学会了”的记录是否可靠 |

验证题与训练题分离；同题族复用需记录，不能把熟悉题目当成迁移。记录延迟测验缺席者，不能直接计为不会，也不能只挑回来参加的学生宣布整体有效。报告效果差异与不确定范围；小试点主要用于发现问题，不预先承诺提升幅度。

## 9. 推荐实施顺序

### 第一期：最小可评估版本

选一门课程的少数代表课时，仅以 PPT 与 HTML 为输入，保留完整播放器，采用已确定的短任务入口。先用同一节课模拟一组初步检查，以及不同回答触发的辅导路径，再确定题量、题型、反馈时点和退出规则；随后实现最少的任务、帮助记录、新题独立尝试和出处展示。抽样核对首批题目与判定，并记录练习负担。课前基础测量只属于可能的效果研究设计，不自动加入学生默认流程。

### 第二期：更有针对性的学习路径

引入按错误类型分流、逐步撤去提示、已会目标减少重复、课后复查、数据库跨设备恢复及教师端学情闭环。用第一期数据调整通过条件与练习负担。

### 第三期：跨课时学习增强

继续保留整段播放，在具备可靠内容对应关系后增加跨课时复习和综合任务。额外目标、题库、量规或图谱只作为可选增强。每项新增能力都需独立验证是否改善学习，避免流程越长而收益不明。
