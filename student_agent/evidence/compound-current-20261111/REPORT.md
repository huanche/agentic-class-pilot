# 最新代码复合要求评估验证

**结论：宽判仍存在，值得修复。** 不是仅有措辞重叠；旧要求把“入队位置”和“无固定队满”两个可分别掌握的意思合为一项，模型只凭后半句证据便确认整项。原场景没有直接整点误切；受控对照证明该宽判可以导致错误整点掌握。

## 方法

遵循 Matt diagnosing-bugs 的真实重放流程，读取项目 AGENTS 和旧风险记录。没有修改业务代码或已有测试，没有提交。脚本 `run.py` 经实际学生命令 HTTP、正常内部平台学习认证协议、真实临时 PostgreSQL、真实配置模型执行；没有替换模型返回。

数据库由仓库 conftest 创建随机独立测试库并在结束删除。没有写入现有学生会话。模型配置仅进程内读取，证据不含API密钥。不是浏览器、公网Cookie BFF或自主模型学生测试。

原始材料：`student_agent/docs/knowledge-teaching/validation/2026-11-10-requirement-progress/run.json` 第6答及前置状态，问题是“front/rear分别指什么，为什么没有队满问题”。学生回答前该点没有学生评估历史。

原回答：学生说 front 指向队头结点、rear 指向队尾结点，链结点动态分配、不像数组有固定末端，只要内存可分配即可继续入队。**没有说明把新结点链接在rear之后，也没有给出可逻辑推出该插入步骤的具体操作。** 知道尾指针指向哪里与会实现入队步骤是不同能力，不能凭后者的名词语义代替操作证据。

待评复合项：`understandingPoints:2`，“入队：在 rear 之后插入，无队满问题”。该项在当前存量课时仍原样存在，未重新提取或替换教材。

## 排除的设置问题

- 前两次准备失败发生在模型调用前：导入旧学生消息违反新观察记录校验；随后缺少本地签名配置。脚本现只导入教师历史，原学生证据留在原assessment_history，设置一次性本地签名配置。没有改产品绕过校验。
- `prior-evidence.json` 的首版正对照提前把整项标demonstrated，会预设结果，排除统计。改为该项unconfirmed、已知部分及历史原话仅包含插入位置，输出另存 `prior-evidence-valid.json`。有效统计7次，另有这1次排除的模型调用，失败/排除不覆盖。

## 重要性与解决建议

优先级高于轻度重复帮助：它直接污染掌握依据，且在最后一项时可提前完成；不过本样例不能推导全课程误判率。

先保持“未提及不记需要帮助”的规则。缺少插入位置时，该复合项应留unconfirmed，不应把没问过的内容记needs_help；也不能因为回答了另一半就demonstrated。

建议方案讨论时优先选：把这种相互独立的评估事实拆成两个证据单元，继续用一个整点任务收集证据，**不要因此多出两道题或改轮数**。对存量课时需要兼容策略，不能仅修新提取提示词就宣称存量问题解决。

若坚持不改条目结构，则模型必须在提交demonstrated前确认累计学生证据覆盖两个意思，允许历史补足，未覆盖不提交该项更新。但旧提示已经要求复合项整体满足，当前仍稳定宽判，单纯再加一句同义提醒的把握较低。证据字段也不能天然消除语义判断错误。

验收应保留这里四种对照：缺半句不确认、完整回答确认、历史补足确认、最后一项不提前完成；不以逐字复述或关键词强匹配替代语义。
