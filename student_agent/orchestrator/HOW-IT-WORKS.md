# 学生端编排器是怎么运行的

本文说明当前学生端的实际运行逻辑。运行代码以 `orchestrator/agent.py` 和 `apps/server.py` 为准；旧版独立骨架与时钟参考脚本已删除，曾有用的设计说明已合并到本文及 [`ORCHESTRATOR.md`](ORCHESTRATOR.md)。

## 一轮课堂请求

会话接口把当前会话状态和本轮输入交给编排器。编排器在 `agent.py` 中依次执行计划加载/恢复、时钟结算、上下文装配、输入分类、教学或主持事件、掌握状态更新、阶段推进判定、状态持久化与回复整理。实际节点和边以 `build_graph()` 为准。

`tick` 用本轮注入的 `now` 与 `stage_started_at`、`lesson_started_at` 做差，得到阶段和整课已用分钟数。编排器不在节点里自行读取系统时钟，因此固定时间戳可以复现相同的计时输入。课程结束后的实际事件也可能由老师的外部控制触发。

## 阶段推进判定

`judge_advance()` 是当前唯一的阶段推进决策点。实际顺序如下：

1. 已结束的课程保持结束。
2. 老师的“下一环节”“结束课程”指令可以越过常规时长门槛；讲解媒体播完也会推进段落或离开讲解阶段。
3. 视频讲解期间等待媒体完成，不因阶段预算到期而切幕。
4. 未达到 `min_stage_minutes` 时留在当前阶段。
5. 达到预算后按 `on_budget_exhausted` 处理：`force_advance` 和 `wrap_up` 推进；`extend` 在超时额度内等待，超限后推进。
6. 其他情况继续当前阶段。

当前实现不再按“证据充分”自动切幕：旧参考脚本曾包含 `advance_when=evidence/either` 和证据触发分支，但生产逻辑已改为时间预算推进，掌握度在课后由 LLM 综合整课对话评估。因此不能把旧脚本里的判定行为当作现行行为。

阶段切换时，`advance_stage()` 记录阶段快照、选择下一启用阶段并重置阶段计时和目标；课程结束时生成总结并落盘。消息轮次结束后会保存会话状态，等待下一次学生或教师输入。

## LangGraph 的结构要点

历史 `graph_skeleton.py` 用示例展示过的核心概念仍适用于理解 `agent.py`：

- 图状态承载会话、阶段、计时、目标、证据和回复等字段。
- 节点通常接收状态并返回部分字段更新。
- 条件路由应读取判定结果；推进规则集中在 `judge_advance()`。
- 阶段快照需要累积保存，不能被下一阶段覆盖。
- 固定时间戳有助于回放计时；LangGraph 的会话持久化由当前应用实际配置决定，不应依据旧骨架注释推断。

旧骨架里的伪实现、占位函数和 `lesson-data/` / `rules/` 文件读取示例已不再维护；以当前平台模式代码为准。
