# 三端架构与接口：团队统一入口

> 团队目标（2026-10-26 确认）：让平台、教师端、学生端各自主要在自己的模块内开发；跨模块依赖通过稳定、可验证的接口表达，内部实现变化不迫使其他端同步修改。不是追求零依赖，也不预设必须拆物理数据库、建副表或引入事件总线。数据库视图可作为所属服务内部的稳定查询层；平台优先通过所属服务 API 消费数据。只有性能、可用性或故障演练证明有必要时，才另行设计副本及可靠同步。

> 状态：设计与现状导航，不是“已全面解耦”的声明。更新日期：2026-10-22。本文描述当前隔离分支 `decouple-implementation`，未表示已推送、合并或部署。

## 先读这三句话

1. 平台管**人和访问资格**，教师端管**课程内容和发布**，学生端管**课堂学习过程**。
2. 目前三端共享 PostgreSQL，平台仍直接读取教师和学生 schema；“服务职责已划分”**不等于**“数据访问已隔离”。
3. 跨服务契约和生成客户端已有一部分，但业务调用尚未全面切换；旧链路仍是运行基线。

本文是给人和 AI 找到正确来源的目录。具体字段以相应 OpenAPI/JSON Schema 为准，实际运行行为还要看提供方代码和回归测试；本文不复制字段清单，以免形成第四份易漂移的接口定义。

## 一张边界表

| 事项 | 权威方（谁能改变事实） | 其他服务需要什么 | 当前状态与目标 |
| --- | --- | --- | --- |
| 用户、会话、角色、选课、课程所有权、平台课程 ID 与教师课程 ID 映射、个人模型配置 | 平台 | 教师/学生后端取得经过验证的身份与授权结论 | 已有服务接口；服务密钥只证明调用服务，不能替代最终用户权限 |
| 课程草稿、资料、课堂场景、课件、知识包、发布/撤销版本 | 教师端 | 平台和学生端只应看到允许学习的发布视图 | 平台现在仍直读 `teacher` schema；目标是可靠发布快照，不让平台改教师原表 |
| 对话、会话、播放进度、掌握度、学习事件 | 学生端 | 平台汇总学情，教师端看被授权的教学视图 | 学生端写 `student` schema；平台现在仍有直读聚合，目标读模型尚未切换 |
| 学生能否看某门课、能否进入某课堂 | 平台的选课/身份结论 **加上** 教师端当前有效发布状态 | 学生端消费授权结果，不自行决定用户身份 | 发布投影不能单独成为权限真相；下架、版本落后、未选课时须拒绝访问 |
| 公共协议：网关路由、部分内部 API、学习上下文、宿主消息 | `contracts/` 的对应源文件 | 三端按版本兼容、经检查生成或消费 | 只有列出的跨服务子集有正式契约；不能推断所有页面 API 都已收录 |

这里的“权威方”是设计边界，不代表已经实现数据库物理隔离、租户隔离或完整多实例能力。SaaS 的组织/学校租户、配额、跨租户安全测试仍需单独设计。

## 四条关键流程（现在 → 目标）

| 流程 | 当前主链路 | 迁移时必须守住的条件 |
| --- | --- | --- |
| 建课/进入课程建设 | 用户经平台入口登录；平台确认教师身份与课程关系，教师端保存课程内容；双方保留课程 ID 映射 | 新建与重试的返回可能分别是 `201`/`200`；不得双发建课或把服务密钥当用户授权 |
| 审核、发布、撤销 | 教师端确认资源、知识包和课堂可见性；平台仍读教师表判断当前发布状态 | 发布和撤销都要覆盖；未来事件/outbox 与版本写入同事务，平台幂等去重、处理乱序与历史回填；旧链路切换前继续权威返回 |
| 学生进入课堂 | 平台结合登录/选课与教师当前发布内容签发或确认进入资格；学生端拿可信上下文，不能相信前端自报用户 ID | 未选课、所有权不符、下架、过期或版本落后时失败关闭；`lessons` 缺失与明确空数组不能混同 |
| 学习与学情回传 | 学生端记录会话、进度、掌握度和事件；经平台学习进度接口汇总，再向教师端提供教学视图 | 学情写入保持唯一权威链路，不双写；重复事件幂等、失败可恢复；平台目前仍有 `student` schema 聚合直查 |

上表是沟通地图，不是完整的时序图或生产事件协议。具体代码从下方“查什么”进入；发布事件、投影、撤销 tombstone、补偿与回滚还处于设计/待实施状态。

## 开发约束：新代码该放哪

- 平台身份/选课规则归平台；教师课程内容及发布写入归教师端；学生会话与学习事件写入归学生端。跨端读取走明确的后端契约或经审查的只读适配器，不新增随手跨 schema 查询。
- 内部 API 变更：先定所有者、调用方、鉴权头、请求/响应、错误和兼容窗口，再修改对应 `contracts/` 源文件、提供方与测试，最后重新生成客户端并跑防漂移检查。
- 不把数据库表结构当接口，也不把生成 SDK 的默认超时、认证、重试和代理行为直接替代现有调用。只读调用可先做结果对比；建课、发布、学情和模型调用不得影子双发。
- 切换数据来源前，保留旧链路权威返回；新投影只做脱敏、限时、限流的影子读取。下架或权限差异一票否决，演练回退后才受控切换。
- 不把历史耦合归零、文件缩短或 HTTP `200` 当作完成标准；验收要覆盖实际权限、数据语义、故障、并发和回滚。

## 下一步按什么顺序做

1. **固定运行基线与关键流程验收**：独立测试库、三端本地联调、教师端全量测试分类；不要在开发/生产库运行会清理数据的测试。
2. **固定接口与依赖边界**：逐调用点核对现有契约缺口；让生成客户端经兼容适配层先接只读调用；可评估 TS/Python 的依赖规则，但规则不替代业务测试。
3. **封装跨 schema 读取**：先保持 SQL、事务、空值和权限语义不变，收拢到只读适配器，留好旧/新结果对比点。
4. **设计并实现可靠发布快照**：教师端发布/撤销与 outbox 同事务；平台做幂等投影、回填、对账和告警；完成影子读取与回滚演练后再切换。
5. **再做内部模块和多实例改造**：消除循环依赖与全局会话状态；会话租约、幂等写入、租户隔离和并发压测另行验收。

任何一步的“测试通过”都要写明范围与日期。无 GitHub CI、独立数据库全回归和真实三端联调时，不宣称可合并生产 `main`。

## 给新同事或 AI 的任务起点

新需求先回答六问：① 哪个服务拥有功能与数据？② 谁是唯一写入者？③ 是否改变跨端接口及兼容窗口？④ 超时、故障、重复请求如何处理？⑤ 对旧用户、旧数据、其他端有何影响？⑥ 如何测试、灰度与回退？若现有边界可容纳，直接在所属模块实现；若需要新增跨端直查、双写或破坏性接口，先做简短架构决策，再改契约和代码。依赖方向/契约检查是防漂移工具，不能替代业务验收。

先回答四问：**改谁的数据？哪条流程？影响哪个契约？旧行为怎样回退？** 然后阅读本页的边界表、相关契约、提供方和调用方代码、对应测试，以及[执行门槛](decoupling-execution.md)。若本页、契约和代码矛盾，标出差异并停止假定“文档一定正确”；不要自行扩大接口或删除旧入口。
