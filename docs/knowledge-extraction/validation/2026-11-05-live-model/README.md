## 首次真实调用发现的接口问题

原始实现的第一次请求返回 HTTP 400：`Thinking mode does not support this tool_choice`，没有产生知识点。见 [原始失败记录](initial-provider-error.json)。

DeepSeek 官方当前默认开启 thinking，而 LangChain ToolStrategy 强制工具选择。按 [DeepSeek thinking 文档](https://api-docs.deepseek.com/guides/thinking_mode/) 的开关说明，在 `extraction_model` 中仅对官方 `api.deepseek.com` 的提取请求设置 `thinking.type=disabled`。模型名、地址、密钥不变；普通教学调用不增加该参数，其他供应商不收到 DeepSeek 专属字段。

这是明确的请求模式适配，不是更换模型或用假模型代替。程序中的生成—校验—反馈修正循环仍然运行。修复后才完成上表两轮成功试验。新增的官方 DeepSeek 及其他供应商回归测试已通过；提取测试共 27 项通过。

## 真实模型的反馈修正证据

自然轮首轮通过，未自然触发结构修正。因此另起一次独立提取，仍使用相同课件和真实模型；在首个 API 响应到达解析器之前，由本机测试器删除第 1 个 concept 的 `details.understandingPoints`。注入前原始提交本身也通过了同一 Pydantic 协议校验，确认本轮故意引入的是这个缺字段错误；其余内容仍来自真实 API。此处是明确标注的故障注入，不是声称模型自己遗漏字段。

框架实际返回的反馈包含：

```text
points.0.concept.details.understandingPoints
  Field required
请按工具参数结构修正并重新提交完整列表，不要改为普通文本。
```

第 2 次真实 API 请求携带上述工具反馈。模型重新提交完整批次，补齐 understandingPoints，Pydantic 结构校验和本地内容编译校验均通过，且未发生第 3 次调用。记录文件保留注入前原始提交、被删除的字段、首轮损坏参数、反馈及第二轮结果，不包含模型内部推理内容。

注入轮第一次原始提交为 13 项，修复后也是 13 项；自然轮是 11 项。两次独立提取在名称、拆分和分类上有所差异，不能把“格式通过”解释为“每次知识点清单完全一致”。

## 内容快速核对及限制

本次仅作开发者快速核对，未进行教师标注评分，不报告准确率。

- 栈/队列定义、操作序列、顺序栈、数制转换、行编辑、顺序队列、循环队列和链队列均有输出，三类型结构可以实际使用。
- 两项 design 分别对应课件中的操作序列设计和整行撤销改造，材料中确有相关练习或拓展要求。
- 自然轮将栈与队列定义合在一个 memory，另列栈术语；独立注入轮拆分成 4 项 memory，且部分知识点在 memory/concept 之间变化。粒度和分类稳定性仍需结合教师意见验证。
- design 的“设计并验证合法出栈序列”同时带有构造与判定要求；后续教学是否需要细拆应由规则讨论决定，本轮没有自动语义拦截或人工改写结果。
- 仅验证一堂课，且输入为画面文字和旁白，不涉及图示、动画或独立公式识别。
- 成功请求返回的 token 统计：自然轮 8145，注入轮两次合计 19957；未计算价格，也不包含未返回 usage 的初始 400 请求。

本机实验脚本与输入快照保留在忽略目录 `.runtime/typed-knowledge-live/`。可审阅的脱敏结果与反馈记录保存在本目录。后续扩大样本时，应先确定教师认可的类型和拆分标准，再评价模型输出质量。
