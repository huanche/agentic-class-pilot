# 课件播放内容的知识点提取改进方案

> 分类：历史方案调研（2026-11-03）。本文件不作为当前实施规范；当前范围以[设计方案](../design/plan.md)为准。

调研日期：2026-11-03。范围：当前代码静态阅读、工具官方文档；没有运行模型对比或测量准确率。以下明确区分已经确认的能力与针对项目的设计建议。

## 结论

建议采用“生成时记录教学结构 + 发布时核对最终课件 + 旧课件按证据块抽取”的双路径，优先完善输入与证据模型，再考虑替换解析器或模型。模型适合做候选发现、语义归并和支持性判断，原文保存、来源定位、关系合法性应由代码执行。结构化输出与第二个模型都不能保证教学判断正确。

## 当前链路与限制

当前播放内容链路主要位于：

- `platform/backend/app/api/routes/student_bridge.py` 的 `_classroom_view`：向学生侧提供场景可见文字与动作；未将完整图片媒体作为视觉输入传递。
- `student_agent/backend/content/context.py` 的 `classroom_materials`：组合画面文字和 speech 旁白，每场景取前 6000 字符。因此图片、图表以及超限部分的知识依据可能缺失。这里是代码层面的覆盖风险，尚不能证明某一次提取错误就是由截断造成。
- `student_agent/backend/content/knowledge.py` 的 `learning_points` / `validate_candidates`：已有原文引用存在性、来源场景、标题包含与最低长度校验。它并非完全没有依据校验，但这些检查无法证明引用真的解释了概念，也无法决定“一个核心概念还是若干并列知识点”。同名重复之外的语义重复仍需处理。
- `student_agent/backend/content/prompts.py`：导入问题不算已教、概念功能合并、不能补常识等教学粒度判断主要写在提示词中。

项目另有 `teacher_agent/lib/server/course-knowledge-extraction.ts` 的课程材料图谱任务，其 top-36 来源片段与每片段 1400 字符限制属于另一条链路，不能用它解释播放内容提取的全部行为。

## 方案比较

| 方案 | 解决的问题 | 代价与局限 | 项目建议 |
| --- | --- | --- | --- |
| 生成课件时同步记录概念与教学结构 | 避免播放完成后再从纯文本猜测设计意图 | 后续编辑可能使记录过期；生成时也可能判断错误 | 新生成课件优先采用，发布时必须与实际场景核对 |
| 证据块选择 + 分阶段抽取 | 减少模型抄错原文，便于区分候选、证据与核心概念 | 仍需语义判断；切块太碎会丢上下文 | 可沿用当前模型与校验框架，最适合先落地 |
| 视觉增强 + 文档结构解析 | 补图片、公式、图表和空间关系 | 增加计算和适配成本；识别结果可能错误 | 对视觉承载知识的场景按需启用 |
| 受控词表 + 别名归一化 | 限定学科范围、稳定概念命名、去重 | 维护词表，且词表存在不代表本课已教 | 有课程标准/教师确认清单时采用，允许新增候选 |
| 标注数据训练专用模型 | 让教学粒度与“已教”判断从实例中学习 | 需要高质量标注及跨课程验证 | 长期路径，先积累教师修改记录 |
| 单纯扩写提示词/加入向量库 | 可改善部分输出或找到相关来源 | 无法单独解决依据缺失与“本课已教”判断 | 作为辅助，不作为此次主要改造 |

表中的项目适用性均为设计推断，不是已经验证的效果结论。

## 建议的实现形态

### 1. 新课件：生成时记录，发布时核对

生成场景时同步输出 `conceptId`、概念名、核心概念/从属要点关系、`sceneId`、`actionId` / `elementId`，并记录“定义、原理、步骤、例子、应用、预告、提问”等教学作用。保留“本来准备教什么”与“最终实际呈现了什么”两份状态。

发布时按最终旁白、文字、图片及动态播放内容核对：只规划但没真正讲解的内容不进入“本课已教”知识点；编辑、删除场景后使旧对齐失效并重新检查。生成元数据只是候选依据，不能直接当正确答案。

### 2. 旧课件：先做完整证据库，再做抽取

将最终播放内容切成稳定证据块，每块保存来源类型、场景/元素/动作标识、原文、字符范围；有可靠的时间信息时再保存开始结束时间，不根据场景编号伪造时间。文字与旁白分别保存，图片记录资源与区域，避免混成不可定位的大段文本。

让模型选择 `evidenceBlockIds`，服务端回填原文与位置，代替让模型重复抄写引文。字符子串检查继续保留为必要校验。证据块存在只能证明“来源可定位”，不能证明“它支持这个结论”。因此还需检查定义/原理/步骤等实质支持，分别保存支持充分、只提及、预告、冲突、缺少依据等状态；有争议时保留为待确认候选。

先逐场景发现候选，再跨场景合并同一概念，建立 `concept -> subpoints -> evidence`。例如“计算机网络”可以包含资源共享等复述要点，避免依靠一段提示词强行把所有输出压成平铺列表。例子、属性、步骤是否独立成为知识点应有明确类型与关系，最终仍需教师反馈校准。

不要通过盲目增加返回数量来解决“依据少”：一个知识点可能需要多个互补片段，也可能只有一段充分定义。优先完整性和语义支持，而非引用条数。

### 3. 视觉与资料：补来源，但保留教学边界

项目自身生成的课件应优先读取已有 DSL、元素、动作和素材引用，按需渲染截图补动态或图形语义。原生结构能够读取时，无需先将全部场景截图后 OCR。

外部 PPT/PDF 可以评估 Docling 或 MinerU。Docling 的统一模型支持文本、表格、图片、层级及来源信息，布局坐标在可用时保存；官方格式清单支持 PDF/PPTX 等。其 PDF 视觉定位示例使用页图及 bbox 将来源高亮回页面。[Docling 文档模型](https://docling-project.github.io/docling/concepts/docling_document/)、[格式支持](https://docling-project.github.io/docling/usage/supported_formats/)、[视觉定位示例](https://docling-project.github.io/docling/_generated/examples/visual_grounding/)

MinerU 官方仓库说明其提供文档解析、OCR/模型解析与结构化输出；PDF/图片与 Office 使用的处理路径不同。选型时应固定版本，以实际 PPT/PDF 样本验证解析质量和资源需求，不能因为支持某种文件就推断其拥有全部视觉理解能力。[MinerU 官方仓库](https://github.com/opendatalab/MinerU)

图像描述仍是模型推断，应保留原图用于复查，不能把生成的描述伪装成教师逐字原话。Docling 提供本地视觉模型图像描述示例，证明这类组件可以接入，但不证明其能准确判断教学知识点。[图像描述示例](https://docling-project.github.io/docling/_generated/examples/pictures_description/)

教材、大纲、标准术语可用于命名与消歧；如果它们没有在本课播放中实际讲解，只能标为扩展资料或候选背景，不能补进“已经教过”的依据。

### 4. 词表与检索的使用边界

SKOS 提供标准标签、别名、上下位和相关概念等组织方式，可借鉴为课程词表结构。它不是知识抽取器；上下位关系也不能直接当先修关系。[W3C SKOS Reference](https://www.w3.org/TR/skos-reference/)

规则匹配可先发现术语与常见定义句式。spaCy 官方文档明确区分词表/模式规则和统计模型，并说明规则可辅助收集训练数据；中文需单独验证分词和学科词表，不能照搬英文示例。[spaCy 规则匹配](https://spacy.io/usage/rule-based-matching)

需要跨很多材料寻找补充证据时，可做关键词与向量召回、重排序；Sentence Transformers 提供召回后 CrossEncoder 重排的官方实现说明。相关度分数不能当作“已经教会”或“引用蕴含概念”的置信度。对于当前单课提取，先保证所有场景参与候选发现，避免用 top-k 检索替代覆盖。[Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

## 渐进落地顺序

1. 先保留完整来源与稳定证据块，修正当前字段丢失及截断策略；在界面支持回到具体场景/原文。
2. 引入核心概念、从属要点、证据作用及“已教支持”状态，抽取改为候选发现、证据选择、跨场景归并。
3. 新课件生成同步记录教学元数据，发布校验最终场景；旧课件继续走抽取路径。
4. 根据真实缺漏补视觉解析与受控词表；积累教师修订，再决定是否训练专用模型。

建议后续验证至少区分漏提、误把预告算已教、颗粒度错误、证据定位错误、证据不支持和视觉信息缺漏；本次没有构建评测集、修改实现或宣称任何准确率提升。
