## 应怎样处理，不应怎样处理

1. **暂不修“5 门草稿课”**：先确认草稿是否预期不注册到平台；只要课程未面向学生发布，不能仅凭无映射删除或补建。
2. **先处理版本认知差异**：若要在本机验证 `final08/09` 的报告逻辑，先在隔离测试库演练迁移、备份和回滚，再按本机启动文档决定是否升级；本次审计不授权直接升级此库。
3. **确认权限边界**：教师端若还在运行时自建表，直接撤 `CREATE` 会造成启动或功能故障。先拆清 `COURSE_DATABASE_URL` 与 `DATABASE_URL` 的实际表归属及建表责任，最后才收紧角色。
4. **优先补测试而非立即加约束**：针对并发选课、章节完成、发布冲突、空 `event_id` 做隔离库测试；确认数据与兼容性后再拟定在线加唯一索引/事务调整。
5. **解耦试点仍可推进**：先做非鉴权学情摘要的只读契约与影子对比；不以这次本地审计替代生产库核验，也不提前切换发布鉴权。

## 待团队决定的边界（建议默认，尚未批准实施）

| 决策 | 建议默认 | 为什么需要拍板 |
| --- | --- | --- |
| 教师草稿何时注册平台课程 | 首次需要平台选课/发布前完成，并支持幂等补偿；草稿可仅在教师端 | 避免把 5 门草稿误判为孤儿，也避免已发布课程无平台身份 |
| 删课/退课后的学习历史 | 不直接跨 Schema 级联删除；先定义保留期限、查询可见性、最终删除/匿名化流程 | 学情与审计可能需要保留，隐私要求也可能要求清除 |
| 学情摘要权威计算者 | 学生端负责原始记录与可授权的聚合；平台负责身份/选课核验与对外组合 | 避免平台永久直查学生表，也避免学生端自己决定教师身份 |
| 发布/撤销的权威 | 教师端唯一写入；平台只维护经对账的只读投影，旧直读在过渡期仍为权威 | 发布状态直接影响学生准入，投影延迟/失败必须 fail closed |
| 租户边界 | 在对外宣称多学校 SaaS 前独立设计 tenant ID、唯一键、行级谓词及跨租户测试 | 现有分 Schema 不等于学校数据隔离 |

下一轮若获准实施，只从**非鉴权读路径**起步：定义响应和鉴权契约 → 学生端只读聚合 → 平台影子比较（旧结果仍返回）→ 差异与超时验收 → 默认关闭开关切换。发布/撤销链路单独立项，不与学情摘要混用验收标准。
