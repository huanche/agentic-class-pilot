# 学生端运行机制

> 写给项目作者本人的导学文档（2026-10-20，对应 `feat/post-video-tutoring` 分支）。
> 读法：第 2 节跟着一个学生的完整旅程走一遍，后面的节回答"为什么这么设计"。
> 所有文件路径都相对 `student_agent/`，行号会漂移，以符号名为准。

---

## 1. 一句话总览

学生端 = **一个不自己做决定的浏览器界面** + **一个替它做所有教学决定的编排器后端**。
前端每 2 秒问一次后端"现在演到哪一幕了"，后端说 `tutoring` 它就显示辅导聊天，说 `ending` 它就显示下课页。所有进度、星级、时间预算的真值都在后端。

三个服务的关系（本地 8088 环境）：

```
浏览器 ──> Caddy 网关 :8088
            ├─ /api/v1/*      → 平台后端 :8080（账号、课程、发布、launch_token）
            ├─ /api/student/* → 学生端 :8000（本文件的主角）
            │   /api/session/*
            │   /api/lesson*
            └─ 其余            → 教师端 :3200（课件、播放器）
```

## 2. 一个学生的完整旅程（主线）

主角：学生小王，大学课堂，平板上打开 `http://localhost:8088`（平台层）→ 登录 → 学生首页点"进入学习"——全程不直接敲 `/app`。

### 2.1 进门：两种入口

代码在 `frontend/src/components/StudentApp.js:32-65`，判定只看一件事——URL 里有没有 `launch_token`：

| 入口                           | 谁在用   | 流程                                                                                                                                                                    |
| ------------------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **平台深链**（正式且唯一的入口） | 真实学生 | 平台层 `8088` 登录 → 学生首页点"进入学习"→ 平台签发一次性 launch_token（HMAC 签名、短时效）→ 深链跳到学生端，拿 token 调`/api/session/start`，身份和课程上下文**以令牌为准**，没有登录页 |
| **独立态**（仅本机调试后门）   | 开发者自己   | 只有 hostname 是 localhost/127.0.0.1 时 `/app` 才显示注册/登录/课程码（OSK7M3）页面。**未登录直接访问 `/app`：非本机一律被 `StudentApp.js` 弹回平台首页 `/`**，不存在绕过登录进学生页的路径                                                                                            |

### 2.2 会话号：一切状态的钥匙

- 独立态：前端自己生成一个 session_id，存 `localStorage["ai-learn.sessionId.<lessonId>"]`（`app.js:32-57`）。
- 平台态：不传 session_id 时，后端用 **(用户, 课程, 课时) 哈希出确定性会话号** `plat-<hash16>`（`apps/server.py` start 端点）。这意味着：小王换台设备、换浏览器再进同一课时，**落回同一个辅导会话**——昨晚续聊功能的换设备场景就是靠这个。

### 2.3 上课：讲解阶段（intro → guided_learning）

- 老师按"开始上课"（`POST /api/session/{sid}/begin`），后端状态机从 idle 起跑。
- 讲解阶段内部有两段：AI 对话段 + 视频段。学生点"开始播放教学视频"进入视频段。
- **视频不是学生端自己的播放器**：是一个 iframe，嵌教师端的课件播放器，地址带 `?embedded=player`——教师端看到这个参数就只渲染场景画布（`teacher_agent/components/edit/PlaybackChromeRoot.tsx`），不显示 AI 圆桌和聊天面板。适配层在 `frontend/src/integration/platform-player-adapter.js`（旧的 `src/platform/playerAdapter.js` 是死代码，别看）。
- 视频每播完一页，教师端播放器发 postMessage（`SCENE_COMPLETED`），适配器转成 `POST /api/session/{sid}/media/done`（`final=false` 只记进度）；**整段播完**发 `PLAYBACK_ENDED` → `media/done`（`final=true`）。

### 2.4 视频播完：进入课后辅导（本次改版的核心）

`media/done (final)` 进后端后（`apps/server.py` 的 `_step` → 编排器）：

1. 全局开关 `AGENT_POST_VIDEO_TUTORING`（默认开）生效时，课堂阶段直接从 `guided_learning` 切到 **`tutoring`**；复述/探究/讨论三个旧阶段被旁路（代码保留，开关关掉就回来）。
2. AI 开场消息**自动到达**，学生不用点任何按钮：列出本节课知识点的固定数字编号（"1. 调度是什么 2. 三级调度……"），并征询四件事——复习顺序、不懂的编号、自评星级（1–5）、复习多长时间，**全部可省略**。
3. 前端原视频页先闪一句"正在进入课后辅导…"过渡文案，然后切到聊天界面，徽标变"课后辅导"——复用讲解阶段那套聊天 UI 和轮询，没有为辅导新做一套界面。

### 2.5 辅导对话：一条消息进来，后端发生什么

学生每发一条消息（统一端点 `POST /api/session/{sid}/message`），编排器的 teach 节点按**确定性骨架**先跑一遍（`orchestrator/agent.py` teach 的 tutoring 分支）：

```
消息进来
  │
  ├─ 意图解析（正则，不用模型）
  │    ├─ 顺序：「先 2 再 1」→ tutoring_order
  │    ├─ 自评：「2 我给自己 2 分」→ tutoring_self_ratings（与系统星级分开存）
  │    ├─ 时长：「复习 15 分钟」→ 服务端记计划结束时间戳（从这条消息时刻起算）
  │    └─ 都没有？看关键词分七类：结束/改时间/自评/选点/追问/求助/答题
  │
  ├─ 如果是"答题"且挂着检测题 → 判答（模型判 correct/wrong/unclear；没模型一律 unclear，星级不动）
  │    ├─ 判对：升星（无提示+未见新题 +1 封顶 5；有提示 ≤3；见过的题 ≤4）→ 推进下一知识点出新题
  │    └─ 判错：第一次同题追问（标记已提示）；连续错 → 讲解 + 换一道**没见过的新题**
  │
  ├─ 如果是"结束" → 切到 ending（见 2.6）
  │
  └─ 组装回复骨架 → LLM 只负责润色成自然口语（模型缺席就把骨架原文说给学生，绝不空窗）
```

几个关键状态键（都在 `ClassroomState` 里声明，随会话落盘）：

| 键                                                         | 存什么                                                                                           |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `tutoring_order` / `tutoring_cursor`                   | 复习顺序（kp_id 列表）和当前推进到第几个                                                         |
| `tutoring_self_ratings`                                  | 自评（kp_id → 1..5），永不进系统星级                                                            |
| `tutoring_planned_minutes` / `tutoring_planned_end_at` | 计划时长与结束时间戳；**到点不关会话**，只在回复里加一句"时间差不多到了——还有想再问的吗" |
| `tutoring_question`                                      | 当前检测题（题干、kp、hint 标记、was_fresh、答错次数）                                           |
| `tutoring_asked`                                         | 已见题干清单——出新题时（优先让模型出，把这份清单喂进 prompt 避开）                             |
| `tutoring_stats`                                         | 答题计数（对/错/提示后对）                                                                       |
| `kp_stars` / `mastery_updates`                         | 系统星级与证据条目（课后反馈的素材）                                                             |

**掌握条**：聊天页顶部常驻一条（`frontend/src/legacy/tutoring-mastery.js`），显示剩余倒计时 + 知识点编号顺序 + 系统星 + 自评。它挂在 `#stage-chat` 第一个子节点，接线在 `app.js` applyServerTurn 的"阶段没变就早退"**之前**——因为倒计时每 2 秒都在变，阶段没变。每个知识点旁有 ⓘ 小图标，悬停/键盘聚焦/触屏点击都能看评分量规。

### 2.6 明确结束：唯一出口

辅导阶段里**没有任何返回/退出按钮**（你的"课堂阶段内无退出"原则）。出口只有一个：学生说"今天就到这"，或者时间到后 AI 问"还有问题吗"、学生回"没有了"。

那一刻（`apps/server.py` 消息端点检测到 tutoring→ending 的切换轮）：

1. 生成**完整反馈**（`tutoring_feedback_payload`）：各知识点终值星级+证据、自评、复习用时、答题统计、未完成的检测、后续建议；另存一份**教师视角摘要**（入库预留，学生端不显示）。
2. 落库：**多版本、只增不改**——每次明确结束一版，学生看的永远是最新版，旧版留着看成长轨迹。
3. 前端落到课后页。

### 2.7 课后页与返回续聊

课后页（`frontend/src/legacy/view-review.js`，路由 `#/review/...`）：

- 学情报告（原有的：知识点星级、阶段表现、建议）。
- **辅导反馈卡**（新增）：第 N 版反馈全文 + "继续辅导"按钮。
- 点"继续辅导"：`POST /api/session/{sid}/resume-tutoring` 把阶段拉回 tutoring（时间/星级/证据/已见题/消息全保留），前端清掉"课时已结束"标记后回聊天页。再结束时生成**第 2 版**反馈。

课程全部课时完成后，课程列表卡片下出现"查看课程反馈"轻量入口，列出各课时的反馈入口。

### 2.8 恢复：刷新 / 重启 / 换设备

| 场景           | 为什么天然恢复                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| 刷新页面       | 会话号在 localStorage，聊天记录按 seq 增量拉回来                                                              |
| 学生端进程重启 | 每轮状态全量落盘`runtime/sessions/<sid>.json`，启动时惰性恢复；剩余时间是**服务端时间戳换算**，不清零 |
| 换设备         | 平台态确定性会话号（见 2.2）                                                                                  |

## 3. 后端怎么想：两层结构 + 状态机

### 3.1 编排器（orchestrator/agent.py）

一张 LangGraph 图（十来个节点），核心循环是 `judge_advance → advance_stage → teach`：

- **judge_advance**（编排核心）：决定要不要切幕。优先级：外部事件（老师按钮/视频播完）> 结束判定 > 阶段规则。辅导阶段的守卫：**没有时间出口**——到点只改教学安排；唯一的 exit 是明确结束。
- **teach**（本幕教学）：**两层结构**是整个学生端最重要的设计——
  1. **确定性骨架**：讲什么、问什么、判定结果怎么落状态，全部普通代码，不碰模型。接不接模型编排都照常跑。
  2. **LLM 只润色**：把骨架算好的指令变成自然语言；判答也是模型出结论、骨架落状态。模型失败/缺席就降级到骨架原文，状态一字不差。

### 3.2 会话层（apps/server.py）

- `SESSIONS` 内存字典 + 每轮落盘（`_persist`），重启恢复（`_restore`）。
- `_step` 每轮：注入时间和外部事件 → 跑图 → 回收状态 → 学习数据同步到平台库（失败不阻塞课堂）→ 落盘。
- 心跳线程每 10 秒推一次时钟（只在课真正开始后）。

## 4. 数据存在哪（三层）

| 层                   | 位置                            | 存什么                                                                                                                                                                                                                                                                                                                              |
| -------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 内存                 | `SESSIONS` 字典               | 当前轮的完整状态（快）                                                                                                                                                                                                                                                                                                              |
| 会话落盘             | `runtime/sessions/<sid>.json` | 全量状态，刷新/重启/换设备的恢复依据                                                                                                                                                                                                                                                                                                |
| 平台库（PostgreSQL） | `student` schema 七张表       | 正式学情：`student_sessions`（会话）、`student_messages`（消息流水）、`learning_events`（学习事件，含辅导的出题/判答事件）、`playback_progress`、`knowledge_mastery`（系统星级 + **self_rating 自评列**）、`task_submissions`、`after_class_reports`（**按 (会话, 类型, 版本) 主键多版本** + 教师摘要列） |

demo 态（`STUDENT_DEMO_MODE=true`）没有库，等价数据写 `runtime/integration/*.json`——同一份 `apps/integration/persistence.py` 代码，只是分支不同。**改持久化逻辑只改这一个文件**，两层自动一致。

## 5. 前端怎么想（frontend/src/legacy/）

- **路由**：`app.js` 顶部一张表。`#/course` 选课时、`#/lesson` 课时 hub、`#/class` 课堂、`#/review` 课后、`#/replay` 回放。
- **阶段→面板映射**：`phases.js` 把后端的 host_phase 翻成界面名（tutoring→chat 复用聊天面板）。前端**永远不自己判断演到哪**，只读后端下发的 host_phase。
- **轮询**：每 2 秒 `fetchSessionState + fetchSessionMessages(since)`，按 seq 去重防双投递（POST 响应和轮询可能带同一条回复）。
- **路由改道**：class/review 路由和"该课时该去哪"不符时弹回课时 hub——这是为什么"继续辅导"必须同时清 localStorage 结束标记、内存课时状态、模块 hostPhase 三样再跳转（`ctx.reopenClassroom()`），少清一样都会被弹回去。

## 8. 设计原则速记

1. **前端不决策**：界面是后端状态的投影，加功能先想"状态机怎么变"，再想界面。
2. **骨架先行，模型可失败**：任何依赖模型的地方，先问"模型挂了这段代码还能不能跑"——编排和星级永远能。
3. **真值在服务端**：时间戳、星级、会话号，客户端只是显示层。
4. **幂等优先**：落库带冲突键、出题带已见清单、结束只在切换轮触发——重复的消息/重放不会写脏数据。
5. **课堂内无出口**：辅导是课堂阶段的延伸，唯一出口是学生明确结束。
